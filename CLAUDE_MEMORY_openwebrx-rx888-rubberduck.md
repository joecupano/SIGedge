Testing OpenWebRX+ setup/install on host **rubberduck** (this machine is rubberduck itself — no SSH needed, work locally). Goal: use the RX-888 with OpenWebRX+ for a session while leaving HackRF/RTL-SDR on ka9q-radio.

**Current state (paused, resume here):**
- `radiod@rx888-wwv.service` stopped+disabled (only that mission — `radiod@hackrf-aprs` and `radiod@rtlsdr-simplex` still running, as intended).
- OpenWebRX+ installed via the **luarvique PPA** (`https://luarvique.github.io/ppa/noble`), package `openwebrx` 1.2.123 — NOT built from source. `dpkg -l openwebrx` should show `ii`.
- Admin web user `admin` created (`sudo openwebrx admin adduser admin`); a pre-existing user `ne2z` was already in `users.json` before this session, untouched.
- ufw: port 8073/tcp opened to "Anywhere" (both v4/v6) at the user's request (originally scoped to a LAN subnet, then widened).
- RX-888 device added in the web UI as `BBRF103 / RX666 / RX888 / RX888 mkII (SDDC) device (via SoapySDR)` using SIGedge's own already-built SDDC SoapySDR module (`/usr/local/lib/SoapySDR/modules0.8/libSDDCSupport.so`, from `packages`/`devices` pkg `SDDC_Driver`, source at `~/SIGedge/source/SDDC_Driver`) — no CUDA/`sddc_connector` needed.
- **Blocked on**: RX-888 SDDC source failing with `[SDDC] ERROR - usb_device: libusb Pipe error` → "SDR device RX-888 MkII has failed". Root cause: the RX-888's FX3 chip only holds one driver stack's firmware at a time (freshly uploaded each power cycle) — ka9q-radio's `radiod` had loaded its own firmware onto the device earlier in the session, so OpenWebRX+'s SDDC driver couldn't talk to it. Fix in progress: physically power-cycle the RX-888 (unplug ~15s, replug) so the FX3 returns to DFU/bootloader mode, then `sudo systemctl start openwebrx.service` so it uploads its own firmware fresh. Also had to `sudo systemctl kill openwebrx.service` first because it was hung in `deactivating (stop-sigterm)` after a broken-pipe websocket error.
- Also: RX-888 device UI sample rate is a fixed list only (2/4/8/16/32/64 MS/s, not free entry) — 64.8 (radiod's native rate) is rejected. Recommended starting point 32 MS/s to avoid CPU/audio stutter, FFT size 16384 (global setting) for resolution, center ~15 MHz for a sane span, gain lives in the profile not the live panel, and a service restart is required before a newly saved profile shows up in the receiver page.

**Key findings from this session, useful beyond just finishing the install:**
- SIGedge's own from-source path (`./SIGedge install openwebrx`, `packages/pkg_openwebrx`) builds plain `jketterl/openwebrx` (not actually "OpenWebRX+") and is broken for RX-888: it never clones/builds `sddc_connector` at all, and that project's current `master` needs CUDA plus `csdr`>=0.19/`owrx_connector`>=0.7 (their `develop` branches) which `pkg_openwebrx` doesn't provide (pins `master` = 0.18.2/0.6.2). Also `m17-cxx-demod` fails to configure because SIGedge's own `codec2` package doesn't install a `codec2Config.cmake`. Real fix used instead: abandon the from-source build, use the **luarvique PPA** — this is what `~/sovereign-sigint` (a sibling project, `scripts/phase6-openwebrx.sh`) already does successfully, and is what "OpenWebRX+" actually refers to.
- `~/sovereign-sigint` and `~/SIGliere` are sibling projects on this same host worth checking before solving an already-solved problem: `sovereign-sigint/docs/openwebrx-sdr-quickstart.md` and `scripts/phase6-openwebrx-rx888.sh` document this exact RX-888/OpenWebRX+ setup in detail (built via a different but equivalent from-source SoapySDDC path, `ON5HB/RX888MK2-Soapy`, since their host didn't already have SIGedge's own SDDC module). `SIGliere` is the AI tier (Ollama/Open WebUI) on this box and explicitly has no SDR/OpenWebRX+ involvement — its CUDA driver (610.43.02, from NVIDIA's own apt repo, `cuda-keyring` already configured) is for Ollama, not relevant to RX-888.
- If ever mixing a from-source build with a PPA/dpkg package for the same app again: **check for `/usr/local/bin` and `/usr/local/lib/python3.*/dist-packages` shadowing the package's `/usr/bin` and `/usr/lib/python3/dist-packages` files** — this caused two real bugs here: (1) a crash-loop (`ImportError: cannot import name 'NoiseFilter' from 'pycsdr.modules'`) because Python was loading a stale from-source `pycsdr` egg via `easy-install.pth`, which also made the package's postinst script fail (`dpkg` showed `iF` half-configured) because postinst itself invokes `openwebrx admin ...`, which crashed on the same import; (2) files that pre-existed before the PPA install (`users.json`, `bands.json`, touched empty by the abandoned from-source script) were left owned by `baldrick` instead of the `openwebrx` system user by the package postinst's `if [ ! -e file ]` guards — the running service (as user `openwebrx`) couldn't read them, so a freshly-added admin user authenticated fine via `sudo openwebrx admin adduser` (root) but failed to log in via the web UI until `chown openwebrx:openwebrx` fixed it.
- `sudo` needs a real TTY in this environment — this session's Bash tool has no cached credential and no NOPASSWD rule, so all privileged commands must be handed to the user to run in their own terminal (chunk them, since a big pasted block can silently stall on an unseen password prompt — confirmed this happened once).
- rubberduck's own LAN IP is `192.168.173.65/24` (`eno1`); the user's laptop's actual source IP across all SSH sessions is `192.168.73.65` — a different /24 (`192.168.73.0/24`, not `.173.`). Easy to transpose; caused one firewall-rule misfire.
- ufw was already active (default-deny incoming) from earlier SIGliere/sovereign-sigint hardening work (`security-hardening.sh`) — ports need an explicit `ufw allow` or they silently timeout rather than refuse.
- `~/SIGliere` (capital L, capital in the middle — not `~/SIGLiere`) is the correct path/casing.
